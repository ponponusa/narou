## ボトルネック分析

### 🔴 Critical: データベース初期化（2.59秒）
**問題点**:
- database.yamlに10,000件のダミーデータ + 実データ
- Database.instanceがシングルトンで全データをメモリ展開
- 毎回2.5秒 + 250MBのオーバーヘッド

**推奨対策**:
1. **インデックス化**: ID/toc_urlベースのインデックスファイル作成
2. **遅延読み込み**: 必要な小説データのみ読み込むlazy loading
3. **キャッシュ機構**: 頻繁にアクセスするデータのみメモリ保持
4. **データベース分割**: ダミーデータと実データを分離

### 🟡 Warning: YAML再パース（1.17秒/3回）
**問題点**:
- 更新チェック時にtoc.yamlを再読み込み
- 3,895件のsubtitles配列を毎回デシリアライズ

**推奨対策**:
1. **差分更新**: 最終更新日時のみ先にチェック
2. **部分読み込み**: 新規エピソードのみパース
3. **JSONへの移行**: YAMLよりパースが高速

### ✅ Good: ファイルI/O操作
- 3,895ファイルの一覧取得: 2.2ms
- 100ファイル読み込み: 31ms
- **評価**: WSL2のファイルシステムは十分高速

## 想定しているTOCチェックの流れ

- 小説ページの目次ページを取得
  - 小説家になろうの目次は、100話ごとに分割されているため、複数ページを取得
  - この作品であれば、38ページ分取得
  - RateLimitを設定しているので、実際の取得時間は38*1.5秒 = 約57秒程度
- 目次ページからエピソードの最終更新日時を抽出
- database.yamlから既存のエピソード情報を取得
- 差分を比較して、新規エピソードや更新されたエピソードを特定
- 必要に応じてエピソードのrawデータを取得
- 取得したrawデータを保存し、toc.yamlを更新
- 更新があった場合、Web UIに通知

## 想定しているTOCチェックの流れに対して、Web UI上での処理時間が長く感じられる

- PushServerでの通知頻度が多くて処理時間に影響を与えている可能性
- 大量のエピソードを持つ小説の場合、目次ページの取得と解析に時間がかかる
- データベースの読み込みと更新処理がボトルネックになっている可能性

## 🎯 並列化実装結果（2025年版）

### 実装内容

**変更ファイル**: `lib/novel/novel_converter/text_processor.rb`

**新機能**: エピソード処理の並列化（環境変数で制御）

**環境変数**:
```bash
NAROU_PARALLEL_CONVERT=true          # 並列処理を有効化（100話以上のみ）
NAROU_PARALLEL_USE_PROCESSES=true    # プロセスベース並列化（推奨）
NAROU_PARALLEL_THREADS=2             # 並列度（デフォルト: CPUコア数）
```

### 技術的詳細

#### GIL (Global Interpreter Lock) の影響

RubyのGILにより、**スレッドベースの並列化ではCPUバウンドな処理の高速化が困難**:

```ruby
# スレッドベース（GILで制限される）
Parallel.map(items, in_threads: 4) { |item| heavy_computation(item) }
# → CPU使用率 99% (1コアのみ)

# プロセスベース（GILを回避）
Parallel.map(items, in_processes: 4) { |item| heavy_computation(item) }
# → CPU使用率 189% (2コア効率活用)
```

#### 実装アプローチ

1. **プロセスベース並列化** (`in_processes`)
   - 各プロセスで独立したConverterインスタンスを作成
   - GILの制約を受けない真の並列処理
   - プロセス間通信のオーバーヘッドあり

2. **スレッドローカルストレージ**
   - 各プロセス/スレッドで独立したConverterを管理
   - Mutexで初期化時の競合を回避

3. **適応的な処理分岐**
   - 100話未満: シーケンシャル処理（オーバーヘッド回避）
   - 100話以上: 並列処理（効果的な高速化）

### 制限事項と今後の改善

#### 現在の制限
1. **プロセス起動オーバーヘッド**
   - 各エピソードごとにプロセス間通信が発生
   - User timeが微増（169.5s → 170.6s）

2. **メモリ使用量の増加**
   - 各プロセスが独立したConverterを保持
   - 2プロセス × 約200MB = 約400MB

3. **進捗表示の制御**
   - 並列処理中の進捗表示が不正確になる可能性

#### 今後の改善案

1. **チャンクベース処理**
   ```ruby
   # 現在: エピソード単位で並列化
   Parallel.map(episodes, in_processes: 2) { |episode| convert(episode) }
   
   # 改善: チャンク単位で並列化
   chunks = episodes.each_slice(1000).to_a  # 1000エピソードずつ
   Parallel.map(chunks, in_processes: 2) { |chunk| convert_batch(chunk) }
   ```
   - プロセス起動を2回のみに削減
   - オーバーヘッド削減で更なる高速化

2. **Ractor の活用（Ruby 3.0+）**
   ```ruby
   ractors = 4.times.map do |i|
     Ractor.new(episodes[i]) { |chunk| convert_batch(chunk) }
   end
   results = ractors.map(&:take)
   ```
   - プロセスより軽量な並列実行
   - メモリ効率的

3. **適応的な並列度制御**
   ```ruby
   optimal_threads = [Parallel.processor_count, episodes.size / 500].min
   ```
   - エピソード数に応じて最適な並列度を自動調整

4. **進捗表示の改善**
   - スレッドセーフなカウンター
   - プロセス間での進捗同期
